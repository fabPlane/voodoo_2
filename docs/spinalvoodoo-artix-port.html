The port is a wrapper job. The core exposes generic SpinalHDL BMB buses on every side, the video output is parallel RGB, and the whole regression suite runs under Verilator against the generic core, so every replacement backend can be proven in simulation before it touches hardware.

What is vendor-neutral found in the source

  • The core's interfaces. One BMB slave for the host (register, LFB and texture-write windows selected by address bits 23:22 in CoreCpuFrontdoor) and six BMB masters for memory, all 32-bit. BMB is SpinalHDL's generic bus, with library bridges to AXI4, Avalon, Wishbone and on-chip RAM.
  • Memories. Fifteen Mem instances, all plain inference: the 257-entry reciprocal table and log table in the TMU, three dither ROMs, four palette RAMs, and the texture cache's meta and bank memories. No vendor macros, no synthesis attributes anywhere in src/voodoo.
  • Arithmetic. Custom fixed-point formats (SQ(48,18) texture accumulators, SQ(48,30) for W) and a reciprocal lookup instead of dividers. Vivado maps these to DSP48E1 slices; a 27-bit Cyclone V multiply becomes two or three cascaded DSP48s, and the 200T has 740.
  • Video. HdmiScanout emits 24-bit RGB with syncs and DE at 640×480 or 720×480, with a CLUT and its own clock domain. That is exactly what the ADV7123 VGA DAC takes, so VGA out needs no new logic.
  • Verification. The Verilator harness, the Glide2x screenshot tests, the DOSBox-X 32-bit Glide path and the trace replay with pixel-by-pixel comparison all target the generic CoreSim. SIM_INTERFACE=de10 already demonstrates swapping the top-level under the same harness.
  • Build. scala-cli, SpinalHDL 1.13, Scala 2.12, no vendor tool in the generate step. Quartus is only invoked by scripts/build-bitstream-de10.

Clocks are not a risk. The DE10 build runs the core at 50 MHz with Quartus router effort set to minimum, which says timing was never tight. Artix-7 -2 is at least as fast as Cyclone V -7. Reaching 90 MHz for Voodoo 2 is a later question about the pipeline, not about the port.

Recommended order least new code first

  1. Reproduce the DE10 memory architecture on the Artix
    All six BMB ports through one arbiter into MIG DDR3. Generate an ArtixTop the way De10TopGen does, add it as a SIM_INTERFACE=artix variant so the Verilator suite runs against it, then build in Vivado. This already beats the DE10, because the DDR3 is no longer shared with the ARM.
    exit: Glide tests pass on the dev board through the PCIe BAR; first bitstream in about two weeks
  2. Move the depth buffer into BRAM
    BmbOnChipRam behind the two aux ports. Verify against the traces in simulation first. Measure the Gouraud+fog+alpha+Z small-triangle row from the README table again.
    exit: the 20% row moves toward the flat-shaded 32% row or better
  3. Move colour buffers to HyperRAM
    Wrap the MJoergen controller in BMB, size the write buffer (fbWriteBufferLineWords, useFbWriteBuffer are already config knobs), and run the DDR bench idea against it. The ISSI part is the device that controller was developed on, so the PHY constraints carry over.
    exit: every row of the performance table at or above the original Voodoo 1
  4. Run the texture cache sizing
    tools/TmuTextureCacheBenchmark.scala exists for this. Fix the BRAM split between depth buffer, texture caches and FIFOs with numbers, before the card layout is frozen.
    exit: BRAM budget on the 200T documented

Decisions to make now they change the board

HyperRAM instead of OPI PSRAM (decided 2026-09-16)

The APS12808L is an OPI Xccela device with no open controller, and JLC has no stock. The card now uses the ISSI IS66WVH8M8BLL-100B1LI: 64 Mbit HyperBus, 3.0V, 100 MHz, about $1.92 in LCSC stock, and the exact part the MJoergen controller was developed on for the MEGA65. Four chips give 32 MB against the Voodoo 2's 4 MB frame buffer; the four channels are for latency, not size. The Infineon S27KL0642 is the same-footprint 200 MHz upgrade.

Phase 1 host path

Use the Artix's hard PCIe block on the dev board with an AXI-lite BAR bridged to BMB. The Glide runtime shim already abstracts memory-mapped access, so the software change is a few lines and the register model is identical to the DE10's. A UART or SPI path would work but is too slow to run games during bring-up.

Reaching Voodoo 2 fill rate 90 Mpixel/s, one pixel per clock at 90 MHz

SpinalVoodoo is already a one-pixel-per-clock pipeline. Its own table shows it: on 1000-pixel triangles it does 51 Mpixel/s textured at 50 MHz, and 41 with alpha and Z, where memory read-modify-write costs the rest. The Voodoo 2 target is the same pipeline at 90 MHz with two texture units in a chain. The gap is not architecture; it is three separate problems.

1. Clock: 50 MHz to 90 MHz

The DE10 build never tried; Quartus ran at minimum router effort. Artix-7 -2 is faster than the Cyclone V -7, and the closed-source ECP5 Voodoo 1 closed at 100 MHz on a slower fabric. A register-balanced fixed-point datapath with DSP48 multipliers runs at 150 MHz on Artix-7, and SpinalHDL makes adding stages cheap. Nobody has measured this core's Fmax on Artix-7, and measuring costs one afternoon: generate the Verilog, synthesise for the 200T with a 90 MHz constraint, read the worst path. Do this first in phase 1. Expect a stage each in triangle setup and the LOD math.

2. Memory: where the original's design was, and where ours differs

The original used three independent 64-bit EDO buses at 90 MHz, one per chip. This card puts the two read-modify-write streams, depth and texels, on chip where BRAM gives each a full port, and leaves only streaming traffic for external memory. Depth in BRAM alone removes the reason the DE10 numbers fall off with Z enabled. Colour worst case is about 400 MB/s against four HyperRAM channels at about 560 MB/s effective, the tightest number on the card. Fallback if it proves tight: render the back buffer in BRAM as well (600 KB fits beside depth) and copy it to HyperRAM at swap, about one millisecond per frame.

3. Triangle rate

The Voodoo 2 sets up three million triangles per second, about 30 clocks each. SpinalVoodoo spends about 80 clocks of overhead per triangle because setup does not overlap rasterisation, which is why its 10-pixel rows sit at 20 to 30% of the original. Overlapping setup of the next triangle with the walk of the current one, and replacing the bounding-box scan with span walking for small triangles, is the one real RTL change. It is contained in TriangleSetup and Rasterizer and is validated by the existing pixel-exact traces.

What the Artix-7 200T brings

  • 740 DSP48 slices against a need of roughly 100 for two TMUs, fog, colour combine and LOD.
  • 13.1 Mbit of BRAM, which is the constraint: 600 KB depth plus texture cache plus FIFOs, or 1.2 MB if the back buffer goes on chip too. tools/TmuTextureCacheBenchmark.scala sizes that split.
  • Enough fabric that 90 MHz is a timing exercise, not a fight. 50% utilisation leaves room for the extra pipeline stages.
Sequence. Measure Fmax on the 200T; put depth in BRAM and watch the alpha-plus-Z rows recover; pipeline triangle setup and watch the small-triangle rows recover; add the second TMU as a chained copy. Each step is measurable against the README table. At 90 MHz with the two fixes the numbers land at or above a real Voodoo 2 across the table.
