The period figures are individual reports from different machines, not a controlled test; they agree on about 25–26 fps, so we are inside that range rather than clearly above it. Sanglard notes that CPU speed made surprisingly little difference: the Voodoo 1 was fill-rate bound in GLQuake, which draws every surface twice (texture pass, then lightmap pass). Our host CPU is much faster, so it feeds commands quicker; that is part of why we match the frame rate while still needing about 1.9 clocks per pixel against the Voodoo 1's ~1. See also Vogons wiki: 3dfx benchmarks.

The design today

  • Clocks: core 48 MHz, DDR3 UI 100 MHz, PCIe user clock 75 MHz; every build ships only if all three meet timing.
  • Memory: 16-bit DDR3 through our own controller; framebuffer colour, depth/aux writes, texture and scanout each get their own AXI path into a DDR adapter with a write collector, a one-line issue buffer and per-port read stagers.
  • Host link: PCIe Gen1 BAR into the Voodoo register / FIFO space; Glide runs on the PC and GLQuake plays unmodified.
  • Display: 640×480 HDMI scanout from DDR, two lines of read-ahead.
  • Verification: Verilator replay of a recorded GLQuake trace with the board's perf counters, unit tests for the DDR adapter and write buffer, and a passive HDMI capture check for visual corruption on every candidate build.

Next: room for Voodoo 2

A Voodoo 2 adds a second TMU (multitexture in one pass, which halves GLQuake's passes), triangle setup on the chip and a 90 MHz clock. Before adding any of that we need space, mainly CLS and registers, so the next step is a resource audit of the current design: what each block costs, and what can move into BSRAM or be shared.
