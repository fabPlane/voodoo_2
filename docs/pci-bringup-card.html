PCI bring-up card

A cheap 5V PCI card with an RP2350B and a T113-S3 and nothing else. It proves the bus interface, the power design, the T113 bring-up and a VGA output before any FPGA board is ordered. A jumper decides who owns the VGA connector.

What it proves and what it does not

Proves

  • The 5V bus-switch front end: the exact chips, footprints and routing the Voodoo card will use.
  • BIOS enumeration on real Socket 7 and Slot 1 boards: config space, BAR assignment, INTA# routing, and the chipset quirks that only show up on hardware.
  • The card outline, bracket, gold fingers and slot power budget.
  • The T113-S3 subsystem end to end: rails and sequencing, SPI NAND boot, Linux, Ethernet, USB, and its LCD port driving a VGA monitor.
  • A DOS and Windows test tool talking to a PCI device you built.

Does not

  • Run anything Voodoo. There is no FPGA.
  • Meet PCI timing to the letter. The RP2350B answers the bus from a polled clock; it works with retry and slow decode, and that is enough to enumerate and exchange data.
  • Move data fast. Expect a few megabytes per second on writes and microseconds per read.
  • Pass through 2D video. One VGA connector, output only.
Why RP2350B and not RP2040. A PCI target needs 46 bus signals. The RP2040 has 30 GPIO. The RP2350B has 48, three PIO blocks with twelve state machines, 520 KB of SRAM to hold a BAR's worth of registers, and costs $1.06. It is the only Pico-class part that fits.

The PCI target on PIO how it answers the bus

Three state machines and a small amount of CPU work. The design leans on two things the PCI spec allows: slow DEVSEL# decode, and Retry, which lets a target say "not yet" without violating anything.

PieceJobMechanism
SM0 watcherCatch the address phasewait 0 pin FRAME#, then on the next CLK edge in pins, 32 for AD and in pins, 4 for C/BE, push to the RX FIFO. DMA copies every transaction header into a ring buffer for the CPU.
SM1 decoderClaim or ignore within 3 clocksIN base set to AD16, so in pins, 16 captures the BAR compare bits into Y; jmp x!=y against X, which the CPU loads with the BAR value after each config write. jmp pin on IDSEL catches config cycles. On a match it asserts DEVSEL# and hands off. About four instructions, 13 to 27 ns.
SM2 data moverComplete data phasesWrites: assert TRDY#, capture AD each clock IRDY# is low, push to FIFO; a DMA pair retargets the destination from the address phase, the same trick PicoDVI uses. Reads: first attempt answers Retry via STOP#; the CPU fetches the word and parity into the TX FIFO; the master's retry completes with TRDY#. Legal delayed-transaction behaviour.
CPUConfig space and register semanticsVendor and device ID, one 256 KB memory BAR backed by SRAM, one 16-byte I/O BAR as a mailbox, command and status registers, INTA# on mailbox writes.

Timing, honestly

PCI wants outputs valid 11 ns after the clock edge. A polled clock cannot do that. What actually matters is that the master samples 30 ns later with 7 ns of setup, so the target has 23 ns from the edge. With the RP2350B at 300 MHz (an overclock it takes easily with a 1.2 V core), one instruction is 3.3 ns; edge detection through wait with the input synchroniser bypassed is about 7 ns, and the out pins that follows lands around 13 to 15 ns after the edge. It fits, with margin that shrinks if the chip runs at the stock 150 MHz. Plan on 300 MHz and verify on a logic analyser through GPIO46.

Nobody has published a PIO PCI target. Bit-banged 100 Mbit Ethernet and DVI exist on these chips, so the raw speed is there, but this is new ground. Budget three to six weeks of PIO work and treat the first goal as "the BIOS lists the device", not "data moves".

T113-S3 subsystem identical to the Voodoo card

This is the part of the bring-up card that transfers unchanged to the FPGA card, so it is built exactly as it will be there: same part numbers, same rails, same boot path.

  • Power. Slot +5V feeds a 3.3V 2 A buck for the card, and the T113's 0.9V core, 1.8V and 1.5V rails with the sequencing from the MangoPi MQ-Dual reference design.
  • Boot and storage. 256 MB SPI NAND, UART0 console on a header, USB OTG for FEL recovery.
  • Network and USB. 100M PHY with a magjack on the bracket, one USB-A host port on the bracket, and the RP2350B as an internal USB device so the T113 can reprogram it and read the transaction log.
  • VGA. The LCD controller drives RGB666 at 640×480 with a 25.175 MHz pixel clock, into an 18-resistor ladder and the 75 Ω load. Good enough to read a console on a CRT. HS and VS through a 74LVC buffer.
  • Software. Buildroot with the mainline kernel, a console on VGA, SSH over Ethernet, and a small daemon that talks to the RP2350B over USB CDC.

Software and test plan each step has a pass condition

  1. Bench: VGA-test mode
    No PC. J-MODE to VGA-test, J-VGA to RP2350. The RP2350 draws a test pattern. Then J-VGA to T113: the Linux console appears. Pass: both sources produce a stable 640×480 image.
  2. In a slot: enumeration
    J-MODE to PCI. A Socket 7 board's BIOS lists vendor 0x1234 device 0x0001 with a memory BAR and an I/O BAR. Pass: lspci on a Linux boot floppy, or a DOS tool using INT 1Ah, shows the device with sensible BARs.
  3. Writes
    The DOS tool writes a 64 KB pattern to the BAR; the T113 reads the RP2350's SRAM over USB and compares. Pass: bit-exact across 1,000 iterations, on at least two chipsets (an Intel 430TX and a VIA MVP3 cover most of the era).
  4. Reads and interrupts
    The DOS tool reads back and verifies. A mailbox write raises INTA#; the DOS ISR acknowledges it. Pass: no hangs, PERR# and SERR# status bits stay clear in config space.
  5. Windows 98
    A stub INF binds the device and a small app maps the BAR. Pass: the device shows in Device Manager without a yellow mark and the app moves data.

Risks specific to this board

  • The polled-clock timing margin. If 300 MHz is not enough on some chipset, fall back to answering everything with Retry and completing on the second attempt. Slower, still enumerates.
  • Parity. Some chipsets flag PERR# and halt. The CPU precomputes parity for read data; if that proves unreliable, set the config-space parity-error-response bit to zero and confirm the BIOS tolerates it.
  • Sharing AD[9:0] with the VGA DAC. The resistor ladder adds about 10 pF and a light DC load to those ten bus lines in PCI mode. Keep the ladder physically next to the jumper, not the switches.
  • T113 first spin. Copy the reference design exactly. This is the one part of the card that carries forward, so mistakes here cost twice.

Path to PCIe how different it is, and how to get there

PCI and PCIe share their software model and almost nothing else. A PCIe device shows up to the BIOS, the OS and the driver as a PCI device: same 256-byte config header, same BARs, same memory-mapped registers, plus a 4 KB extended config space. Everything below that is different.

The practical plan: design the PCI target and the bus switches so the card is happy at 3.3V signalling, which costs nothing. That makes the commercial adapter work immediately and keeps the bridge-chip variant open. Keep native PCIe as the option for a later, faster GPU, since the phase 1 dev board work already exercises the Artix PCIe block.
