# Steps 2 and 3 of the open-flow port: core fit, then DDR3

Companion to `PCIE-OPEN-PLAN.md`. Written 11 Oct 2026. Step 1 (Pro Dock
package in yosys/nextpnr/apicula, blinky on hardware) is done.

Ground rules for anyone working these steps:

- Work in a dedicated git worktree, never in `~/projects/vodoo_2` itself
  (another agent keeps uncommitted vendor-flow work there).
  Step 2 lives on branch `open/pcie-apicula` (worktree `~/projects/vodoo_2-open`),
  step 3 on `open/ddr3-phy` (worktree `~/projects/vodoo_2-ddr3`).
- Builds never touch the board. Anything that does (openFPGALoader, openocd,
  `ddr3_jtag.py`) goes through `fpga/hw/gowin/board-lock -m "why" -- cmd`.
  An SRAM load kills the vendor PCIe design until the host reboots, so do
  not load bitstreams on the dock without the user's go-ahead; build and
  pack only. Vendor `gw_sh` builds are fine (licence is flaky, retry).
- Toolchain: `~/opt/oss-cad-suite/bin` (yosys, nextpnr-himbaechel,
  gowin_pack). Chipdb for the Pro package:
  `fpga/hw/gowin-open/chipdb-GW5AST-138C-fpg676.bin`, regenerated by
  `gen-fpg676-chipdb.sh`. Pack with `PYTHONPATH=~/projects/fabPlane/apicula-head`
  so the fork's database (which has the FPG676 package) is used.
  Only that apicula commit (cd6d492) with the Education 1.9.11.03 data
  overlay and the `fabplane/gw5ast-pincfg-const` nextpnr archgen routes; see
  `gen-fpg676-chipdb.sh` and the recipe in PCIE-OPEN-PLAN.md.
- Commit and push often (`git push origin <branch>`).

## Step 2: Voodoo core without PCIe or DDR3 through yosys/nextpnr

Goal: find out whether nextpnr can place and route the SpinalVoodoo core on
the GW5AST-138 at all, what primitives are missing, and how long it takes.
The vendor flow needs 4 min synth + 20 min PnR for the shrunk core and
still left 495 nets unrouted at 94 % CLS, so this is the real test of the
open flow.

Inputs:

- `fpga/rtl/gowin/TangMega138kPro.v` (9.9 MB, plain Verilog from Spinal,
  no vendor primitives inside) plus its `*.bin` ROM sidecars. Regenerate
  with `sbt "runMain voodoo.gowin.TangMega138kProGen"` if needed;
  `GowinGenSupport.config` in `CoreGowinGen.scala` is the one Gowin config
  (useTexFillCache=false, GowinMemStylePhase register/BSRAM split).
- `fpga/hw/gowin/src/board_top.v` shows how the vendor wrapper connects
  PLLs, DDR3 IP, DVI TX and PCIe. We replace all of that.

Sub-steps, each a commit:

2a. **Wrapper.** `fpga/hw/gowin-open/rtl/voodoo_core_open.v`: instantiate
    `TangMega138kPro` (or `CoreGowin` directly if the Pro top drags PCIe
    ports) with PCIe TLP ports tied off and the DDR3 native UI replaced by
    a stub that acks writes and returns a pattern on reads (keep a small
    BSRAM-backed window so the core's framebuffer path exercises real
    logic). Keep HDMI pixel outputs as plain IO (no DVI TX) or drop to a
    heartbeat; the point is fabric fit, not video. Makefile target
    `voodoo_core` with `TOP := voodoo_core_open` for that target only.
2b. **Yosys.** `synth_gowin -family gw5a`. Record LUT/FF/BSRAM/DSP counts in
    `build-pro/voodoo_core-synth.log`. Expected trouble: `$mem` inference
    into BSRAM (SP/SDPB/DPB) and `$mul` into MULT/PADD. If yosys leaves
    `$mem_v2` or `$mul` cells, see which apicula bels exist for gw5a in
    `apycula/gowin_pack.py` / `gowin_arch_gen.py` and map manually
    (`memory_bram -rules` with a gw5a rules file is the usual fix).
2c. **nextpnr placement.** `--device GW5AST-LV138FPG676AC1/I0 --chipdb ...
    --vopt cst=tang_mega_138k_pro_open.cst`. Add the pins the wrapper
    uses to the CST. First run with `--placer heap --no-route`? No: use
    `--timing-allow-fail` and let it run; watch for "no BELs remaining"
    (missing bel types) and ALU/DFF0 placement failures (the DFF0 skip
    patch in `projects/nextpnr` is known to break ALU chains, do not use
    it). Record placement time and utilisation.
2d. **nextpnr routing.** Himbaechel's router is single-threaded. Budget
    hours, run detached (`setsid nohup ... > build-pro/voodoo_core-pnr.log`).
    If it fails to converge, shrink the core via `GowinGenSupport.config`
    (enableFog/enableChromaKey/enableAlphaTest/enableDither, maxFbDims)
    rather than fighting the router; each cut is a separate data point.
2e. **Pack.** `gowin_pack --cpu_as_gpio -d GW5AST-138C`. A packed `.fs` is
    the deliverable even unflashed. Record end-to-end wall time next to
    the vendor numbers in PCIE-OPEN-PLAN.md.

Deliverables: wrapper, Makefile target, CST additions, a results table
(yosys cells, nextpnr placement/routing time, unrouted count, pack time),
and a list of missing bels / yosys mapping gaps with the nextpnr error
text verbatim.

## Step 3: DDR3 on the open flow

Goal: an open replacement for `DDR3_Memory_Interface_Top` (encrypted Gowin
IP). The vendor `ddr3_test` build shows what the hard PHY uses:

| Primitive | Count | In apicula for GW5AST? |
| --- | --- | --- |
| IDES8_MEM | 32 | no |
| OSER8_MEM | 40 | no |
| OSER8 | 25 | GW5A only, verify on GW5AST |
| IODELAY | 32 | no |
| DQS | 4/24 | no |
| DDRDLL | 1/4 | no |
| CLKDIV | 1/24 | not on GW5AST (HDMI demo blocks on it) |
| PLL | 1/12 | yes (fork) |

Source: `fpga/hw/gowin/ddr3_test/impl/pnr/ddr3_test.rpt.txt`. The IP core
RTL is encrypted, so everything comes from fuzzing: build many vendor
bitstreams that differ in one primitive or one parameter, diff the `.fs`
files, and derive the fuse tables, exactly how apicula was built for
earlier families.

Sub-steps:

3a. **Harness.** `fpga/hw/gowin-open/ddr3-fuzz/`: a script that takes a
    small Verilog design + CST, runs `gw_sh` (source `fpga/hw/gowin/env.sh`,
    device `GW5AST-138B GW5AST-LV138FPG676AES`, ~1.5 min each, run several
    in parallel in separate dirs; the vendor PnR is single-threaded) and
    stores `impl/pnr/*.fs` plus the `.rpt.txt`. A diff tool that turns two
    `.fs` into a list of (tile row, col, bit) differences; apicula's
    `apycula/fuse_h4x.py` / `fuzzer` tooling in the fork is the starting
    point, GW5AST tiles are 1-indexed in the `.fs` the same way.
3b. **Baseline primitives one at a time.** Minimal designs, each with one
    instance and the rest a passthrough, placed by `INS_LOC`/`IO_LOC` to a
    known IO: `IODELAY` (sweep `C_STATIC_DLY` 0..255), `OSER8_MEM`,
    `IDES8_MEM`, `DQS` (per bank, the four used by the dock's DQS pins
    J4/H7/B5/C1), `DDRDLL`, `CLKDIV`. The GW5A IDES8/OSER8 bels in apicula
    give the port lists; the `_MEM` variants add `FCLK`/`PCLK` and
    `RESET`/`DQSR90`/`DQSW0`/`DQSW270` from the DQS block. Gowin's
    `IDE/data/device/GW5AST-138C/*.dat` carries the primitive port maps.
3c. **Fuse tables into apicula.** Add bels + fuses to the fabPlane fork on
    top of cd6d492 (branch from `apicula-head`), regenerate the msgpack and
    chipdb, add the bels to nextpnr's `gowin_arch_gen.py` /
    `pack.cc` on the `fabplane/gw5ast-pincfg-const` branch.
3d. **Open PHY + controller.** Once the primitives place and fuse, the
    controller choice is LiteDRAM (`litedram` generator, gowin target
    exists for GW2A/GW5A-style PHY in some forks) or a hand-written
    DDR3-800 controller reusing the native UI that
    `Axi4ToGowinDdrNative.scala` already targets. Calibration (read
    leveling via DQS/IODELAY sweeps) is the hard part; the vendor's
    `ddr3_jtag.py` BIST is the acceptance test, through board-lock, once
    the user allows board time.

Deliverables for a first night: 3a working end to end on one primitive
(IODELAY sweep showing which bits move), the fuzz harness committed, and
the primitive port lists extracted from the `.dat`/vendor netlists for
3b. Anything past that is a bonus.

## Open questions to settle early

- Does yosys `synth_gowin -family gw5a` know GW5AST DSP (`MULT12X12` etc.)
  and BSRAM widths used by the core? If not, step 2 may need the generic
  `synth` + manual `techmap`.
- Does the vendor router's 495 unrouted nets mean the core simply does not
  fit this die, in which case nextpnr will not do better and the real fix
  is upstream area work in `ext/SpinalVoodoo`?
- The Gowin licence server is flaky; step 3 fuzzing needs dozens of builds,
  so a retry loop in the harness is required.
